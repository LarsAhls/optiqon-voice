## 8. Revoke: the device blocks, and the revocation is server-visible

**Corrected 2026-09-09 (finding F1).** The earlier version of this step asserted 403 on the
tester's own `users/{uid}` document. That is provably wrong: `firestore.rules` grants
`allow get: if signedIn() && userId == uid();` deliberately **not** gated on approval, so an
account can learn that it is pending, rejected or revoked — and `tests/rules/m1.test.mjs`
asserts that this read *succeeds* for a revoked account. The old criterion would have produced
a false FAIL on the one step meant to prove the security boundary.

Note the limit this exposes: in Mission 1 **no client-visible Firestore path is gated on
`isApproved()` for a non-admin** (`isApproved()` is reachable only through `isReader()` /
`isWriter()`). A tester's whole cloud surface is that one status-independent document. So
cloud-side refusal on revoke is **not observable here**, and G3 proves the *device* boundary,
not the cloud boundary — recorded as UNPROVEN in `docs/BACKEND_OPEN_CONTRACTS.md`.


No re-approval of the revoked tester and no destructive cleanup is performed to obtain a

## Two defects found and fixed between Phase D and step 5

Both were durability failures around the deliberate `exitProcess(0)` that an identity change
performs, and both were found on the device rather than in a test.

**Sign-out did nothing** (`e4a1e68`). `auth.signOut()` records the change with `apply()`; the
process ended before that write reached disk, so the next start read the account back. Fixed by
resetting the onboarding answer first — in the root being left *and* in the root the next
process opens — dropping the identity last, and flushing Firebase's own record synchronously.

**Sign-in did not stick** (`c2d8378`). The same race, mirrored, and the more damaging of the
two: signing in bound the new storage root and then lost the credential, so the account screen
asked to register again however many times Lars signed in — on both accounts and both profiles.

Evidence, read off the device at 17:10:

    storage_bindings.xml   written 17:06   active_uid=qHWdyXbVQWcxaoI496gdk1rFwVt2
    com.google.firebase.auth.api.Store.*   written 17:03   <map />

The two disagreed: the app believed an account was active that Firebase no longer knew about.
The flush now happens in `ProcessRestarter` on the way out of the process rather than at the
call site that happens to remember it. Confirmed after the fix — same files, same device:

    active_uid=qHWdyXbVQWcxaoI496gdk1rFwVt2
    Store.*.xml = 7336 bytes, containing qHWdyXbVQWcxaoI496gdk1rFwVt2

and Lars, in the app: "förbi 1 & 4 och är inloggad".

These are not smoke-test steps. They are recorded here because a physical smoke that had not
been run would never have found them: both are invisible to the unit suite, which cannot end a
process, and both broke the very first thing a beta tester would do.

#### F8 — step 6's instruction cannot work as written *(measured, correction proposed)*

The template says "force a refresh (background/foreground)". It cannot produce the failure on a
recently verified account. `AccessRefresher.refresh()` throttles every trigger except
`UID_CHANGE` and `MANUAL`: a `FOREGROUND` trigger first asks `isStale()`, which requires the
stored verdict to be at least `CHECK_IN_INTERVAL_MS` = **15 minutes** old. Below that it returns
`RefreshOutcome.Throttled`, which is deliberately not published, so `lastOutcome` stays
`Confirmed`, the state stays `Active`, and `SessionBanner` renders nothing at all. The
`FAIL_REFRESH` flag sits further in, in `DebugRegistrationReader`, and is never reached.

This cost a full cycle of "it looks the same as usual" before it was traced. The only
unthrottled path from the UI is **Settings → Konto → "Kontrollera igen"**
(`AccountSettingsSection.kt:105` → `refreshNow()` → `RefreshTrigger.MANUAL`), and that is what
actually produced the banner.

#### F9 — debug flags do not survive a process restart *(measured)*

`AccessDebugControls` holds `failRefresh` and `clockOffsetMs` in memory. Android may kill the
app between two adb commands, and a broadcast to a stopped package starts a *fresh* process with
both back at their defaults — silently, with the hook still reporting success for the command
that set them. Any step spanning more than a moment must re-assert the flag and check the
process identity (`pidof` plus `stat /proc/<pid>`) before trusting the state. This matters most
for step 9, where `CLOCK_OFFSET` has to hold across a grace expiry.

**Proposed, not applied:** both findings belong in `G3_SMOKE_TEMPLATE.md` so the next run does
not repeat them. The approval box lists the F1/F2 template corrections by name and does not
cover these, so the template is left untouched pending Lars's word; the findings live here in
the working record meanwhile.

#### F10 - the offline banner arrives too late to explain anything *(UX finding, not a test defect)*

The banner exists to tell an offline user why dictation will not work. It cannot do that job as
wired: the session state only becomes `Degraded(OFFLINE)` when a refresh *attempts* and reports
`NoNetwork`, and foreground triggers are throttled until the stored verdict is 15 minutes old
(F8). Dictation and session refresh are separate paths, so a user goes offline, dictates,
fails, and still sees `Active` with no banner - for up to a quarter of an hour, unless they
happen to press a button in Settings. In this run the banner appeared only because it was
asked for explicitly.

The per-dictation error is what actually informs the user today, and it is worded well. The
banner is the redundant half, and it is the half the smoke template treats as the evidence.
Worth a decision before beta: either drive the state from a failed dictation, or drop the claim
that the banner is what tells people they are offline.

#### F11 - the counter counts attempts, not successes *(affects how earlier steps read)*

`TranscriptionManager.upsertHistory` inserts a row for a *failed* transcription too, carrying
`status` and `errorMessage`. So `dictations` in the dump is a count of attempts: it moved
2 -> 6 -> 9 across this step without a single successful round trip. Steps 5 and 6 are
unaffected because they rest on `dictation_words`, which only a successful transcription can
raise (0 -> 5 -> 9, and it stayed at 16 through every failure here). The distinction is
recorded so that no later reader mistakes the row count for evidence of a working provider.

### A defect found and fixed during step 7 - the bubble does not appear on a tapped text field

Reported by Lars mid-step: in airplane mode, tapping into a text field did not raise the
recording bubble; restarting the app raised it. Seen again later, and later still *not*
reproducible - intermittent. Airplane mode is the context, not the cause.

`TextInjectorService.isKeyboardVisible` lives in a companion object, so it outlives both the
service and the bubble it describes. The check was edge-triggered - report only when the value
changes - and ran only on `TYPE_WINDOW_STATE_CHANGED`. Once the cached flag says "keyboard
visible" at a moment when no bubble is on screen, no edge can ever arrive to correct it:
`BubbleService` shows the bubble from that same flag at start-up, which is exactly why
restarting the app worked.

Fixed by re-stating the truth at the moment the user expects the bubble: an editable field
taking focus now re-checks the IME and reports a visible keyboard even when the cached value
already said so. `showBubble()` is idempotent, so re-stating costs nothing. The rule is
extracted as `shouldReportKeyboard(...)` and pinned by `KeyboardVisibilityReportTest` (4
cases). Suite: **332 testcases, 0 failures, 0 errors**.

This is app code and therefore outside the G3 box. It was made on Lars's explicit instruction
during the run, and is recorded here rather than folded silently into the gate's evidence.
The fault was intermittent, so the fix was argued from the mechanism and pinned by a test
rather than proven by a reproduction. **Confirmed on device afterwards**: on the installed
build, Lars tapped into text fields repeatedly, without restarting the app, and the bubble
appeared every time. Closed.

### Two method findings from the step 9 attempt (2026-09-09 ~20:00-20:35 CEST)

**F12 - implicit debug broadcasts are not delivered after the 20:02:52 reinstall.**
`adb shell am broadcast -a se.optiqon.voice.debug.<ACTION>` - the form the receiver's own
KDoc documents - returns `Broadcast completed: result=0` with **no `data="..."` field**, and
nothing happens: `AccessDebugControls` is not written, `DUMP_STATE` does not rewrite
`files/debug/state*.txt`, and no `AccessDebug` line reaches logcat. `cmd package
query-receivers` confirms the receiver is registered and exported behind
`android.permission.DUMP`, so this is delivery, not registration. Naming the component
explicitly works and returns the result string:

```
adb shell am broadcast --user 0 -n se.optiqon.voice/.debug.AccessDebugReceiver \
    -a se.optiqon.voice.debug.CLOCK_OFFSET --el offsetMs 345600000
Broadcast completed: result=0, data="clockOffsetMs=345600000"
```

The **presence of `data="..."` is the tell** that a hook actually ran. The earlier installation
did accept the implicit form (state dumps at 18:37 and 19:39 prove it), so step 6's evidence
stands; this is a post-reinstall behaviour. Roughly twenty minutes of step 9 attempts were
made against silently discarded broadcasts before this was found, and those attempts tested
nothing. Every debug hook from here on names the component.

**F13 - `am force-stop se.optiqon.voice` disables the accessibility service on this device.**
After a force-stop (used to get a clean process for the grace-expiry baseline), `settings get
secure enabled_accessibility_services` returned `null` and `accessibility_enabled` returned
`0`, where both had named `se.optiqon.voice/.service.TextInjectorService` a minute earlier.
Without the accessibility service there is no keyboard signal, `BubbleService` never receives
`onKeyboardVisibilityChanged`, and the bubble cannot appear - so dictation cannot be started
at all. Re-enabling an accessibility service is a security setting and a human action; it is
not something this session does on Lars's behalf. Recorded so that no later step mistakes a
missing bubble for a product defect.

**Method note for step 9 - the open UI is the wrong instrument.** `AccessRepository.decision`
(`AccessRepository.kt:91`) emits `evaluate(snapshot)`, then arms `delay(remainingGraceMs)`
**once**, from the clock as it was at that moment. Changing `clockOffsetMs` afterwards does not
re-arm that deadline, so an already-open screen does not flip to blocked no matter how far the
debug clock is moved. That is not a product defect - a real 72 h passage does fire the deadline,
and the KDoc already concedes Doze - but it means the offset must be read where the live clocks
are read. `currentDecision()` is documented as "the authority", reads the live clocks, and is
what `AccessGuard.authorize()` uses at the point of action and what `BubbleService.onCreate()`
uses to refuse to start while blocked. **Step 9 is therefore proven by attempting a dictation,
not by watching a screen.**
