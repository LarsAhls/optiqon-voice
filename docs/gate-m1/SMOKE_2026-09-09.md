if it is not greater, build with `-PversionTag=v<YYYYMMDD>.<patch>`. A refused install is not
a data risk — the phone stays on the old version — but it is a stop.

## 8. Revoke: the device blocks, and the revocation is server-visible

**Corrected 2026-09-09 (finding F1).** The earlier version of this step asserted 403 on the
tester's own `users/{uid}` document. That is provably wrong: `firestore.rules` grants
`allow get: if signedIn() && userId == uid();` deliberately **not** gated on approval, so an
account can learn that it is pending, rejected or revoked — and `tests/rules/m1.test.mjs`
asserts that this read *succeeds* for a revoked account. The old criterion would have produced
a false FAIL on the one step meant to prove the security boundary.

Note the limit this exposes: in Mission 1 **no client-visible Firestore path is gated on
`isApproved()` for a non-admin** (`isApproved()` is reachable only through `isReader()` /
`isWriter()`). A tester's whole cloud surface is that one status-independent document. So
cloud-side refusal on revoke is **not observable here**, and G3 proves the *device* boundary,
not the cloud boundary — recorded as UNPROVEN in `docs/BACKEND_OPEN_CONTRACTS.md`.

```
node scripts/admin/m1-bootstrap.mjs revoke <tester e-mail> --project optiqon-voice-47498 --apply
```

Before the device notices, export the tester's current ID token to the scratchpad **only**:

```
$HOOK $PKG.debug.EXPORT_ID_TOKEN
$ADB shell run-as $PKG cat files/debug/id-token.txt > "$SCRATCH/id-token.txt"
$ADB shell run-as $PKG rm files/debug/id-token.txt
# Probe 1 — own document. Expect 200 with status "revoked".
curl -s -w '\n%{http_code}\n' \
  -H "Authorization: Bearer $(cat "$SCRATCH/id-token.txt")" \
```

## Rollback, and what is not authorised

Live Auth and Firestore changes are **not automatically reversible**. Two Auth users, two
`users/{uid}` documents, `config/limits`, `config/counters` and `admins/<adminUid>` persist
after the run; the tool has no delete, no undo and no counter reset by design. The tester's
documents stay (synthetic account); removing them is a separate, separately approved cleanup.
No re-approval of the revoked tester and no destructive cleanup is performed to obtain a
green result.

If step 1 fails the phone keeps the previous version. **Never** re-install an older APK over
the migrated database (the old build's destructive downgrade would erase it). Uninstall,
clear-data, an older APK and any other destructive step require Lars's separate explicit
approval — the decision that the old data is expendable does **not** pre-approve a method.

## What a filled-in table does not mean

**A filled-in smoke table is not a pass.** G3 = PASS only when every mandatory test passes:
real Google sign-in **and** the e-mail link; a genuinely separate tester `localId`; the full
lifecycle pending → blocked → approved (seat +1) → dictating → revoked → device blocks; a real
end-to-end ASR → LLM → injection round trip; the negative tests (degraded-in-grace, offline,
grace expiry by clock offset, sign-out mid-recording); account isolation in both directions;
and the corrected step 8 criteria. Any mandatory test that fails *or cannot be verified* makes
the run **PARTIAL or STOPPED**, and the report then names the exact remaining blocker.

#### F8 — step 6's instruction cannot work as written *(measured, correction proposed)*

The template says "force a refresh (background/foreground)". It cannot produce the failure on a
recently verified account. `AccessRefresher.refresh()` throttles every trigger except
`UID_CHANGE` and `MANUAL`: a `FOREGROUND` trigger first asks `isStale()`, which requires the
stored verdict to be at least `CHECK_IN_INTERVAL_MS` = **15 minutes** old. Below that it returns
`RefreshOutcome.Throttled`, which is deliberately not published, so `lastOutcome` stays
`Confirmed`, the state stays `Active`, and `SessionBanner` renders nothing at all. The
`FAIL_REFRESH` flag sits further in, in `DebugRegistrationReader`, and is never reached.

This cost a full cycle of "it looks the same as usual" before it was traced. The only
unthrottled path from the UI is **Settings → Konto → "Kontrollera igen"**
(`AccountSettingsSection.kt:105` → `refreshNow()` → `RefreshTrigger.MANUAL`), and that is what
actually produced the banner.

#### F9 — debug flags do not survive a process restart *(measured)*

`AccessDebugControls` holds `failRefresh` and `clockOffsetMs` in memory. Android may kill the
app between two adb commands, and a broadcast to a stopped package starts a *fresh* process with
both back at their defaults — silently, with the hook still reporting success for the command
that set them. Any step spanning more than a moment must re-assert the flag and check the
process identity (`pidof` plus `stat /proc/<pid>`) before trusting the state. This matters most
for step 9, where `CLOCK_OFFSET` has to hold across a grace expiry.

**Proposed, not applied:** both findings belong in `G3_SMOKE_TEMPLATE.md` so the next run does
not repeat them. The approval box lists the F1/F2 template corrections by name and does not
cover these, so the template is left untouched pending Lars's word; the findings live here in
the working record meanwhile.

The banner exists to tell an offline user why dictation will not work. It cannot do that job as

banner is the redundant half, and it is the half the smoke template treats as the evidence.

### A defect found and fixed during step 7 - the bubble does not appear on a tapped text field

Reported by Lars mid-step: in airplane mode, tapping into a text field did not raise the
recording bubble; restarting the app raised it. Seen again later, and later still *not*
reproducible - intermittent. Airplane mode is the context, not the cause.

`TextInjectorService.isKeyboardVisible` lives in a companion object, so it outlives both the
service and the bubble it describes. The check was edge-triggered - report only when the value
changes - and ran only on `TYPE_WINDOW_STATE_CHANGED`. Once the cached flag says "keyboard
visible" at a moment when no bubble is on screen, no edge can ever arrive to correct it:
`BubbleService` shows the bubble from that same flag at start-up, which is exactly why
restarting the app worked.

Fixed by re-stating the truth at the moment the user expects the bubble: an editable field
taking focus now re-checks the IME and reports a visible keyboard even when the cached value
already said so. `showBubble()` is idempotent, so re-stating costs nothing. The rule is
extracted as `shouldReportKeyboard(...)` and pinned by `KeyboardVisibilityReportTest` (4
cases). Suite: **332 testcases, 0 failures, 0 errors**.

This is app code and therefore outside the G3 box. It was made on Lars's explicit instruction
during the run, and is recorded here rather than folded silently into the gate's evidence.
The fault was intermittent, so the fix was argued from the mechanism and pinned by a test
rather than proven by a reproduction. **Confirmed on device afterwards**: on the installed
build, Lars tapped into text fields repeatedly, without restarting the app, and the bubble
appeared every time. Closed.

1080x2376 frame. All hooks sent with the explicit component (F12).

**Baseline.** `clockOffsetMs=0`, `failRefresh=false`: bubble present, tap starts a recording
(0:04 timer seen). So the instrument works and the account is Active.

**Attempt 1 - offset alone is not enough while the device is online.** `CLOCK_OFFSET
345600000` (4 days) with `failRefresh=false` **granted** the dictation. The phone shows an
airplane icon but Wi-Fi is on inside airplane mode - Chrome loaded a live page over it - so the
pre-check refresh in `AccessGuard.authorize()` succeeded and stored a fresh APPROVED verdict.
The ~4 s recording was cancelled with the bubble's own cancel control and the audio discarded;
no ASR and no LLM call was made.

**Attempt 2 - the offset poisons the very snapshot it is meant to age.** With
`failRefresh=true` **and** `CLOCK_OFFSET 345600000`, the dictation was **still granted**.
Cause: the refresh in attempt 1 ran *while the offset was already applied*, and
`AccessRepository.record()` stamps `verifiedAtWallMs`/`verifiedAtElapsedMs` from the same
`DebugClock`. The stored verdict was therefore dated T+4 d, and read back at the same offset
its age was minutes - comfortably inside the 72 h grace. **A clock offset can never expire a
snapshot that was recorded under that same offset.** This recording was cancelled the same way.

**Attempt 3 - PASS.** Keeping `failRefresh=true` and moving the offset *past* the poisoned
stamp - `CLOCK_OFFSET 691200000` (8 days), giving the stored verdict an age of ~4 days against
a 72 h grace - the same tap on the same bubble produced **no recording**. The bubble turned red
and showed only its retry and dismiss controls. Broadcast results
`data="clockOffsetMs=691200000"` and `data="failRefresh=true"`; pid still 30947.

**Correction to the recipe in section 9 above.** `CLOCK_OFFSET --el offsetMs 259200001` on its
own is only sufficient on a first, never-refreshed snapshot. Once any refresh has succeeded
under an offset, use one of:

- set `FAIL_REFRESH --ez enabled true` **before** any `CLOCK_OFFSET`, so no verdict is ever
  stamped through the shifted clock; or
- move the offset well past the poisoned stamp, as done here (8 days against a stamp made at
  +4 days).

Either way `FAIL_REFRESH` must be true at the moment of the tap, or an online device simply
refreshes the grace away.

discriminators:

1. The access path calls `updateState(ServiceState.Error(...))` **directly**, whereas every

   state 90 seconds later (screenshots at 20:44 and 20:45). Only the access path does that.
2. `AccessGate.evaluate()` can only return `GRACE_EXPIRED` here: the uid did not move, a
   snapshot exists and its status is APPROVED, so the sole remaining branch is `isWithinGrace`
   being false. `NOT_REGISTERED` would require an identity change, which nothing in this step

## F19 — API key not carried over after sign-out/sign-in (reported by Lars, 2026-09-09, **not diagnosed**)

Lars reports that after signing out and signing back in and choosing to use the settings already
on the device, the API key does not come with them and has to be entered again.

What the device actually holds, read on both users of `01132f9f`:

```
shared_prefs/storage_bindings.xml (user 0)   default_owner = qHWdyXbVQWcxaoI496gdk1rFwVt2
                                             binding_qHWdyXbVQWcxaoI496gdk1rFwVt2 = default
shared_prefs/storage_bindings.xml (user 10)  default_owner = ptojAKrVGJP1PQ71GUx2QJTCIPj2
                                             binding_ptojAKrVGJP1PQ71GUx2QJTCIPj2 = default
```

So both accounts have **claimed** the default root, the binding is committed to disk, and
`SecurePreferencesStore` never deletes a key — it only ever writes one
(`SecurePreferencesStore.kt:44-50`). Signing the *same* account back in resolves to the same root
and the same `secure_settings.xml`, so the stored key should still be there.

Two readings remain, and they are not the same problem:

1. **The same account signs back in and the key is on disk but not shown.** This is the reading
   the evidence already supports, and F16 above is half of it: a sign-out clears
   `onboarding_complete` on the root being left while leaving that root's encrypted keys intact.
   The next sign-in therefore walks back through onboarding — and onboarding starts from
   `OnboardingUiState.apiKey = ""`, nothing prefills it from `SecurePreferencesStore`, and
   `canVerify` refuses to move on while it is blank. So the app demands a key it is already
   holding. The stored key is not lost; the CONNECT step simply never reads it. That is a real
   defect and a fixable one: prefill the field from the current root, and treat an existing
   verified key as already satisfying `canVerify`.
2. **A different account signs in.** Then an empty key field is the isolation working as
   designed: the default root is already claimed, `canClaimDefault` is false, the new account is
   allocated its own empty root, and handing it the previous account's key would be exactly the
   leak §10 forbids.

Which of the two it is depends on which address was used, and that has not been established.
**Not investigated further inside G3** — it is outside the approved box, and reproducing it means
signing the admin out mid-gate. Recorded here as an open finding for a separate box.

## F18, confirmed in the field — and it is worse than "the button is missing"

While the work copy was signed in as the tester and in front, dictation attempts made *for the
test account* were captured, transcribed, cleaned and stored by the **personal profile's** app.
Read back at 22:32 on `01132f9f`:

| | user 0 (admin) | user 10 (tester) |
|---|---|---|
| `dictations` | 2 → **5** | **0** |
| `dictation_words` | 12 → **34** | 0 |
| `dictation_texts_sha256` | `37D9102E…BA10A6` → `4D2AE1E8…2FF47D3` | `E3B0C442…B855` (empty) |
| `asr_api_key_sha256` | `5441BA9A…9BBA` | `94A807E4…A24D` |

Nothing leaked between the two apps — each used its own key and its own storage root, and the
tester's counters stayed at zero. The failure is the other one: because Android binds
accessibility services only for the current user, the **only** bound injector on the phone is
user 0's, so it is user 0's app that hears the microphone, spends user 0's key and writes user
0's history, no matter which profile the person believes they are dictating into.

For a beta that is a real hazard rather than a cosmetic gap: a work-profile install looks
signed-in and configured, and quietly routes the user's speech and their API spend to the other
account on the phone. **A work profile must not be offered as a way to run a second account.**
The supported route is the app's own account switch inside one Android user.
